## Part 1 — Self-critique of the first audit

1. **I audited what exists instead of what's missing.** I never asked the first business question: _what does a paying customer get?_ Answer, verified by grep: `subscription_tier` is written by the Stripe webhook and read in exactly two places — a badge on `/settings` and a badge in `/admin/users`. **No feature, route, component, or API checks it.** The first audit ranked billing bugs P0 while missing that a perfect billing pipeline would currently sell nothing.
2. **I mistook silence for health.** "Zero runtime errors in 7 days" with 2 users, no error tracker, no analytics, no web-vitals, and a healthcheck that returns HTTP 200 with `database:"error"` is not health — it is absence of instrumentation.
3. **I never checked delivery process.** There is no `.git` directory in the production folder. No history, no rollback of source, no CI gate, no second machine. Deploys go up via CLI token from one Windows desktop. Every other finding is downstream of this.
4. **I skipped the AI surface entirely.** `/api/advisor`, `/api/twin`, `/api/trinity` are unauthenticated LLM proxies guarded only by a per-lambda in-memory limiter. I quantify the spend exposure below.
5. **I trusted the DB because advisors were quiet.** The schema is clean (exactly the 15 rebuild tables), but `schema_migrations` still holds ~90 phantom rows from the old prototype — including versions future-dated to **May 2027** — which will fight every future migration workflow.
6. **"Email templates exist" — I moved on.** `/api/email` is called by **nothing** in the codebase. Welcome, verdict, and reassessment emails never fire. And Supabase auth email is presumably on built-in SMTP (2–4 emails/hour) — signup confirmations break at trivial scale.
7. **Auth completeness unverified.** There is **no password reset flow at all** — zero hits for `resetPasswordForEmail`/forgot/recovery in the codebase. A user who forgets their password permanently loses their account.
8. **Flat severity list, no engineering economics.** No effort estimates, no acceptance criteria, no sequencing rationale, no tradeoffs, no "what NOT to build."
9. **Unverified relays.** I repeated an agent claim that `.env.production` was "committed" — there is no repo to commit to, and the file itself is clean (publishable values only, correctly documented). Conversely I missed: no canonical URLs across three live hosts, Vercel team appears to be on the **Hobby** plan (`"plan":"hobby"` in the OIDC token claims), and share links have **no revocation** path.

## Part 3 — Findings register

### TIER 0 — Existential (process & business). Do these before touching features.

**T0.1 — No version control.** Only `.gitignore` exists; no `.git`. Failure modes: any bad edit is unrecoverable; no diff review; no blame; no rollback of source (Vercel can roll back builds, not your working tree); total bus-factor of one machine. **Fix:** `git init` + private GitHub repo + connect Vercel Git integration (kills token deploys, adds preview deploys per branch) + branch protection on `main` + CI running `typecheck && test && build` on every push. **Effort: half a day. Acceptance: a PR with a failing test cannot deploy.**

**T0.2 — Monetization is decorative.** Evidence: `subscription_tier` read only in `settings/page.tsx:63` and `admin/users/page.tsx:62` (display). No entitlement checks anywhere. Failure mode: paid users get nothing; free users get everything; churn is guaranteed and revenue is accidental. **Fix:** create `lib/entitlements.ts` — one function `getEntitlements(tier)` returning capabilities (e.g. `advisorMessagesPerDay`, `fullReport`, `familySeats`, `partnerSharing`) — enforced server-side in API routes and server components, not in client code. Pick 2–3 genuinely premium capabilities (advisor depth, full report/credential export, family mode) and gate them. **Effort: 1 day for the layer + first three gates. Acceptance: a free-tier request to a gated API returns 402/403 in an integration test.**

**T0.3 — Zero observability.** No error tracking, no product analytics, no web vitals, `version: "1.0.0"` hardcoded in healthcheck (can't tell which build is live), healthcheck returns HTTP 200 when the DB is down (monitors watching status codes will sleep through an outage). **Fix:** Sentry (client+server, source maps via the Vercel integration), PostHog (or Plausible if you want cookie-free) with a minimal event schema — `assessment_started/completed`, `verdict_shown{verdict}`, `override_recorded`, `checkout_started/completed`, `share_created` — plus `@vercel/analytics` vitals; healthcheck: return 503 when `database:"error"`, and inject `VERCEL_GIT_COMMIT_SHA` as version. **Effort: half a day. Acceptance: a thrown error in prod appears in Sentry with a commit SHA; funnel numbers visible next morning.**

**T0.4 — No password reset / password change.** Grep proof: zero `resetPasswordForEmail`, `updateUser`, "forgot", "recovery" hits. **Fix:** `/auth/forgot-password` (calls `resetPasswordForEmail` with redirect), `/auth/reset-password` (recovery-session `updateUser`), link from sign-in, password change in settings Security. Depends on T3.6 (SMTP) to actually deliver. **Effort: half a day. Acceptance: full reset round-trip on prod domain.**

**T0.5 — Vercel plan appears to be Hobby.** Evidence: OIDC token in `.env.local` carries `"plan":"hobby"` for team homi-tech. Hobby prohibits commercial use (ToS), no SLA, tighter function limits, no team seats. **Fix: verify in dashboard; upgrade to Pro before charging a single card. Effort: 15 minutes + $20/mo.**

**T0.6 — Migration history pollution.** Remote `schema_migrations` holds the full prototype lineage (00001–00034, 2026-04→06) _plus_ ~35 rows future-dated 2026-08 → **2027-05** (`cms_schema`, `document_extractions`, `email_jobs`, `mirror_*`, …) that sort _after_ the July rebuild. Schema itself is clean (verified: exactly 15 rebuild tables). Failure mode: any future `supabase db push` / `migration list` reconciliation sees ~90 migrations that don't exist locally and either refuses or "repairs" in the wrong direction; new files can collide with phantom versions. **Fix:** delete phantom rows (everything except `20260706193938…20260707224634`) via `supabase migration repair --status reverted` or direct SQL on `supabase_migrations.schema_migrations`, then commit the 11 real files as the canonical lineage. **Effort: ~1 hour, zero risk to data. Acceptance: `supabase migration list` local ≡ remote.**

### TIER 1 — Security & money path

**T1.1 — Share IDOR (cross-tenant score leak).** `app/api/shares/route.ts:30–38` inserts `body.assessmentId` unchecked; RLS insert policy only validates `created_by`. Any authenticated user can mint a public 30-day share link for **any** assessment UUID, and `get_shared_assessment` (SECURITY DEFINER, anon-executable) serves the victim's scores. The bitter detail: the correct pattern already exists **in this codebase** — `assessments/override/route.ts:51–60` does the exact ownership select before mutating. The gap is consistency, not capability. **Fix (mirror override):**

```ts
const { data: owned } = await supabase
  .from("assessments")
  .select("id")
  .eq("id", assessmentId)
  .eq("user_id", user.id)
  .maybeSingle();
if (!owned) return NextResponse.json({ error: "Assessment not found." }, { status: 404 });
```

Plus tighten the RLS insert policy with an EXISTS subquery so the API can never regress. **Effort: 30 min + test. Acceptance: cross-user share attempt returns 404 in an integration test.**

**T1.2 — Billing state machine is one-third built.** Current event coverage:

| Stripe event                    | Today                                                   | Consequence                                                                                   | Required                                                        |
| ------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `checkout.session.completed`    | ✅ (but see below)                                      | —                                                                                             | keep                                                            |
| `customer.subscription.updated` | ❌ ignored                                              | downgrades, `past_due`, `cancel_at_period_end` never propagate — users keep paid tiers unpaid | map price→tier, status→`subscription_status`                    |
| `customer.subscription.deleted` | ✅                                                      | —                                                                                             | keep                                                            |
| `invoice.payment_failed`        | ❌ ignored                                              | no dunning state, no user messaging                                                           | set `past_due`, trigger email                                   |
| any handler DB failure          | ❌ returns 200                                          | Stripe never retries → **paid, unprovisioned customer, silent**                               | return 500 on transient failure                                 |
| duplicate delivery              | ❌ no idempotency store                                 | double-processing on retries                                                                  | `webhook_events(event_id unique)` insert-first                  |
| anonymous checkout              | ❌ allowed                                              | money taken, `client_reference_id` null, webhook skips, nothing granted, no recovery          | 401 unauthenticated `/api/checkout`                             |
| couponed/prorated price         | ⚠️ falls back to matching hardcoded 999/2499/3999 cents | tier resolution fails on any discount                                                         | enforce `lookup_key` on every Stripe price; drop cents fallback |

**Tradeoff — hand-rolled vs official SDK:** the manual HMAC verify is correct (timing-safe, tested against the spec by inspection), but the official `stripe` SDK gives typed events, `constructEvent`, and future-proofing for ~200KB of dependency. At your stage: adopt the SDK; keep the raw-body handling. **Effort: 1 day incl. idempotency migration + fixture tests. Acceptance: replayed event processes once; simulated DB failure→Stripe retry→provisioned; test-clock downgrade lands in the profiles row.**

**T1.3 — Unauthenticated LLM endpoints = open spend faucet.** `advisor` allows 20 req/min/IP, `max_tokens:1024`, 12-message history at ≤4,000 chars each. Worst-case call ≈ 13k input + 1k output tokens ≈ **$0.05**. Within the advertised limiter, one IP can burn **~$60/hour, ~$1,400/day** — and the limiter is per-lambda (T1.4), so real exposure is a multiple of that under concurrency. There is no Anthropic budget cap wired to alerting; discovery channel = the invoice. Secondary: the client supplies `assessment` context, so the companion will earnestly counsel forged numbers (integrity, not security). **Fix:** require auth for LLM routes (advisor already only matters post-assessment; keep the `/artifact` demo behind `demoContext` with a much tighter anonymous budget, e.g. 5/day/IP), enforce a per-user daily message quota server-side (this is also your natural premium entitlement, T0.2), move limits to Redis, set an Anthropic workspace spend cap + alert. **Effort: half a day.**

**T1.4 — Rate limiting is architecturally void.** `lib/ratelimit.ts` is a `Map` in lambda memory: every concurrent instance has its own counter and every cold start resets it. Under any parallel load the effective limit is `N_instances × limit` — unbounded. Coverage is also inverted: LLM/scoring/waitlist have (broken) limits, while the _write_ routes have **none**: `/api/assessments` (unbounded inserts), `/api/shares`, `/api/checkout`, `/api/billing/portal`, `/api/account/delete`, `/api/account/export`, `/api/plaid/*`. **Fix:** Upstash Redis behind the existing `rateLimit()` signature (sliding window), applied to every mutating route. Alternative considered: Vercel WAF rate rules — good as an additional coarse layer, but you want per-user keys, which needs app-level Redis. **Effort: half a day.**

**T1.5 — No Content-Security-Policy.** `next.config.ts` sets HSTS, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy — CSP is the missing one that matters; there is currently no second line of defense against XSS on pages holding financial self-report data. **Fix:** start `Content-Security-Policy-Report-Only` with `default-src 'self'; connect-src 'self' https://*.supabase.co https://api.anthropic.com; script-src 'self' 'unsafe-inline'` (Next inline chunks), watch a week of reports, then enforce (nonce-based if you want to drop `unsafe-inline`). **Effort: half a day + one week soak.**

**T1.6 — Internal error leakage.** Raw `error.message` / upstream bodies returned by `/api/assessments:76,81`, `/api/checkout:77`, `/api/assessments/override:71,97`, `/api/email:93` (Resend body), `/api/plaid/exchange:59`. Postgres error strings can disclose schema/constraint names. **Fix:** log server-side (→Sentry), return generic message + correlation ID. **Effort: half a day sweep.**

**T1.7 — Shares cannot be revoked.** Only `POST /api/shares` exists; fixed 30-day TTL, no DELETE, no UI listing active links. A regretted or leaked link stays live for a month; kill switch is a manual DB delete. For a product whose B2B thesis is _consumer-controlled_ score sharing ("Consumer-authorized", "Expires 30 days" on the landing), revocation is not a nicety — it is the promise. **Fix:** `DELETE /api/shares/:id` + "Active share links" list in settings with revoke buttons + `revoked_at` check inside `get_shared_assessment`. **Effort: half a day.**

**T1.8 — Minor hardening.** Waitlist email enumeration (`{already:true}` → return uniform `{ok:true}`); no Origin/CSRF check on cookie-authed POSTs (SameSite=Lax covers modern browsers; add an origin allowlist for depth); two divergent zod schemas for the same assessment payload (`/api/scoring` vs `/api/assessments` — consolidate into `lib/validation/assessment.ts`).

### TIER 2 — Product integrity (why it doesn't feel finished)

**T2.1 — A third of the product is unreachable, and the app has no signed-in shell.** `(product)/layout.tsx` renders the _marketing_ header; it always shows "Sign in" (`SiteHeader.tsx:63,95`) even to authenticated users. Nothing links to `/dashboard` or `/settings` except redirects. Fully orphaned working routes: `/trinity`, `/twin`, `/decisions`, `/signals`, `/credit`, `/calendar`, `/family`, `/connections`. **Fix:** auth-aware shell — server component reads the session, renders user menu + product nav (Dashboard, Assessment, Tools, Companion, Journal, Settings) and relegates marketing nav to signed-out state. This is the single highest-leverage UX item in the codebase. **Effort: 1–1.5 days.**

**T2.2 — The flagship funnel loses data.** `FullAssessmentFlow.tsx` keeps all answers in `useState`; zero draft persistence (grep-verified). Loss matrix: refresh → gone; accidental back-swipe → gone; mobile tab eviction (rampant on iOS Safari) → gone; sign-in mid-flow → gone. Every loss event at step 15 of 17 is a churned user at peak intent. **Fix:** persist `{version, form, index, updatedAt}` to localStorage on change, offer "Resume where you left off" on mount, clear on submit; version-stamp so schema changes invalidate cleanly. **Effort: half a day. Acceptance: kill the tab at step 15, reopen, resume.**

**T2.3 — `/results` and `/plan` ignore the database.** Both render exclusively from localStorage. Signed-in user on a new device: dashboard shows history, results says "No results yet" — the app contradicting itself about the user's own score. **Fix:** fall back to latest DB assessment when signed in; local result wins only when newer. **Effort: half a day.**

**T2.4 — The landing page contradicts the engine — live, today.** Permissioned Readiness Summary card: score **82** labeled **ALMOST THERE**, six sections below a spectrum declaring READY = 80–100. Canon: `engine.ts` thresholds are boundary-inclusive; 82 is READY. For a company whose entire moat is _verdict integrity_, the flagship page disagreeing with the engine is a brand wound. **Fix:** make it 76 or 78 (keeps the "warm timing" narrative) — one line in `(marketing)/page.tsx:352`. Then add a unit test that any hardcoded marketing score/verdict pairs import `scoreToVerdict()` — turn brand canon into CI. **Effort: 5 minutes + 30 for the guard test.**

**T2.5 — The 45-question bank is dead code.** `lib/questions/bank.ts` (and its DB seed, 45 rows live in `question_bank`) is imported by zero runtime files; the real flow is 13 hardcoded field-steps. Decide: **(a)** wire the bank in (dynamic rendering from DB enables A/B, per-decision question sets, and the multi-decision platform vision — 2 days), or **(b)** delete the mirror and let the 13-step flow be the truth (2 hours). What's untenable is a "45-question canonical assessment" that ships as 13 questions with a 1,200-line ghost. Recommendation: (a) — the question bank _is_ the platform play.

**T2.6 — Split-brain persistence.** DB-backed: journal, daily, calendar, family, outcomes. localStorage-only: finance (900-line dashboard!), credit, couples, genome, plan progress, advisor thread — and the companion widget uses _sessionStorage_ while advisor chat uses _localStorage_ (same persona, different amnesia). Users cannot form a model of what survives. **Fix (redesign, not rebuild):** one `lib/persistence.ts` contract — local-first, background-synced to DB for signed-in users — applied feature-by-feature, starting with finance and the advisor thread. **Effort: 2–3 days across features.**

**T2.7 — Plaid connect succeeds and forgets.** `plaid/exchange` discards the access token by design (no `plaid_items` table). If Plaid env keys are ever set, users will complete Link and watch the connection evaporate. **Fix now:** keep the feature env-gated _and_ hide the connect UI. **Fix later (before enabling):** `plaid_items` table with token encrypted via pgsodium/KMS — never plaintext, plus item webhook handling. **Effort now: 30 min; later: 2 days.**

**T2.8 — Internal playground in the public footer.** `SiteFooter.tsx:15` links `/artifact` ("Companion Playground", self-described internal test environment) on every page including for logged-out visitors. Remove from footer; keep the route (it's your demo harness) behind a flag or `/dev` convention. **Effort: 5 minutes.**

**T2.9 — Transactional email is built and disconnected.** Four polished templates + a secured `/api/email` route (internal-secret header — good) called by nothing. No welcome on signup, no verdict email after assessment, no reassessment nudge — i.e., **the retention loop doesn't exist**. The reassessment reminder is arguably the product's core retention mechanic ("re-take the read in 30 days" is on the landing page as a promise). **Fix:** trigger welcome from auth callback, verdict from `/api/assessments` on save, reassessment via Vercel cron (`vercel.json` cron → route scanning assessments older than 30 days, respecting an unsubscribe flag). Requires Resend domain verification (SPF/DKIM for homitechnology.com). **Effort: 1 day incl. cron + unsubscribe.**

## Part 5 — Backwards-engineering from the billion-dollar outcome

**The asset is not the app. It is verdict integrity plus the outcome dataset.** Credit scores became infrastructure because lenders trusted the number. HōMI-Score becomes infrastructure only if (a) the number is unforgeable and consistent everywhere it appears — you already built server-authoritative scoring, which is why T2.4's 82/ALMOST-THERE is a strategic bug, not a typo — and (b) you can eventually _prove the verdicts were right_. The schema already contains the crown jewel and treats it casually: `user_override` + `outcome_surveys` (day30/90/365) is ground truth linking predictions to real-world outcomes. No competitor has it; it is the training data for "Decision Readiness Intelligence" as a defensible claim rather than a tagline. Instrument every verdict, override, and survey completion from day one (T0.3), and never let the survey loop silently fail — it currently has no delivery mechanism (T2.9's cron is also _this_).

**The wedge is the Permissioned Readiness Summary.** The landing page already sells it ("Consumer-authorized · Readiness receipt · Verified · Expires 30 days"). The B2B product is a **verification API**: partner presents token, gets a signed, expiring, revocable, minimal readiness receipt. Today's share system is 60% of that — what's missing is exactly T1.7 (revocation), T1.1 (integrity), and a receipt-verification endpoint with partner API keys. When you build B2B, build it _there_, not as a new surface.

**Sequencing (exit criteria, not dates):**

- **Phase 0 — Trust the rails** (≈ week 1): T0.1–T0.6, T1.1–T1.4. _Exit: CI green gate; a paid test-mode subscription provisions, downgrades, and cancels correctly; one IP cannot spend more than $5/day of LLM; cross-tenant share test fails._
- **Phase 1 — Ship the product you already built** (≈ weeks 2–3): T2.1–T2.9, T1.5–T1.7, T3.3, T3.6. _Exit: a new user can sign up, confirm by email, take the assessment without data-loss risk, see results on any device, navigate to every feature, pay for something that visibly unlocks, reset a forgotten password, and revoke a share._
- **Phase 2 — Compound** (months 2–6): question-bank-driven assessments (T2.5a) → second decision category; outcome-survey delivery + first cohort analysis; readiness-receipt verification API with partner keys; persistence unification (T2.6).

**What NOT to build now:** native mobile (PWA manifest already covers the gap), more tools/calculators (eleven is plenty; zero are discoverable — that's T2.1), a CMS, tRPC/GraphQL (route handlers + zod are correct at this scale), microservices/monorepo (a single Next app on managed Postgres is the right architecture until well past product-market fit — the things that must scale, Vercel and Supabase scale for you once the in-process state is gone, which is exactly T1.4). **Cut or flag off:** `/credit`, `/couples` (thin, single-device, dilutive), `/connections` until Plaid persistence is real.
